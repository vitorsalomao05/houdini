# Architecture Decision Records (ADRs)

Short, dated, reversible. Each records *what* we decided and *why*, grounded in the June 2026 research.

## ADR-001 — Read JSON endpoints, don't scrape a background browser
**Decision:** Default fetch path is a native `URLSession` call to the provider's JSON endpoint, authenticated with a credential read from the Keychain. The "open Chrome in background and reload" idea is demoted to a last-resort fallback adapter.
**Why:** A proven reference (`ttar-p/claude-usage-widget`) reads the Claude Code OAuth token from Keychain and calls `api.anthropic.com/api/oauth/usage` directly. This is ~6 MB vs hundreds of MB of bundled Chromium, survives UI redesigns, and avoids JIT entitlements / nested-binary notarization hell.
**Trade-off:** Endpoints are undocumented/unversioned and can break; we mitigate with last-good caching and clear auth-expiry handling.

## ADR-002 — WidgetKit cannot do 60s; menu bar app is the flagship
**Revised 2026-07-03** (in place, per ADR-013). Two corrections to the original text: (1) **Übersicht is historical** — that surface was removed and no longer exists in the product; references to it below record the June-2026 context, not a live surface. (2) The Notification Center WidgetKit widget was never built — it is **planned, not shipped** (`apps/widget/` is a README-only placeholder whose deletion is ratified per ADR-013; git history preserves it). The true-60s experience is the **menu bar app process**, which hosts both 60s surfaces: the menu bar item and the native NSPanel desktop widget (ADR-013). The reload-budget constraint below stands unchanged and is one reason WidgetKit is deferred.
**Decision (original, 2026-06):** The true-60s experience is the **menu bar app** (and Übersicht). The Notification Center WidgetKit widget is shipped as a *glanceable, ~15-min* surface with honest copy.
**Why:** Apple gives widgets a daily budget of ~40–70 reloads (effective ~15–60 min); minimum entry spacing ~5 min; even host-app `reloadAllTimelines()` is throttled and deferred. Debugger has no limit, which misleads. This is a hard platform constraint, not a bug we can engineer around.
**Trade-off:** We must set user expectations; if/when a WidgetKit widget ships (ADR-013 re-entry), we market it as "glanceable," not "live."

## ADR-003 — All-Swift shared core (no bundled Node/Chromium by default)
**Revised 2026-07-03** (in place, per ADR-013). The Übersicht surface referenced below was removed (historical), and no macOS WidgetKit widget target exists (deferred — ADR-013). Today `FetcherCore` has two shipping consumers: the menu bar app (which includes the NSPanel desktop widget in-process) and the `houdini` / `houdini-selftest` CLIs; the unbuilt iOS scaffold also imports it (ADR-008). The all-Swift/no-Chromium decision itself is unchanged.
**Decision (original, 2026-06):** `FetcherCore` is a Swift package consumed directly by the menu bar app and widget; the Übersicht `.jsx` calls a tiny Swift CLI (`houdini`) or curls directly. No Node/Playwright in the default build.
**Why:** Bundling Chromium roughly doubles engineering effort *just for code signing* (bottom-up signing, JIT entitlements `allow-jit` / `allow-unsigned-executable-memory`, library-validation disable). All-Swift keeps hardened-runtime signing trivial. Only adopt a bundled headless browser if a target provider truly has no readable endpoint.

## ADR-004 — Claude first, OpenAI/Console secondary, ChatGPT Plus experimental
**Decision:** Build the Claude Pro/Max adapter first (cleanest signal). Anthropic Console + OpenAI Platform admin-API adapters second (zero ToS risk, documented). ChatGPT Plus quota is experimental/best-effort.
**Why:** Claude exposes `utilization_pct` directly behind the user's progress bars. OpenAI has no clean consumer quota number; only "limit reached" signals. Don't promise a gauge we can't reliably fill.

## ADR-005 — Credentials in Keychain, never on a server
**Decision:** All tokens/cookies stored in macOS Keychain; no Houdini backend ever receives them. Embedded WebView login for cookie-based providers; offer to reuse Claude Code's OAuth token when present.
**Why:** The app touches logins; trust is the core adoption barrier. This also becomes the landing-site privacy story.

## ADR-006 — Distribution: ad-hoc-signed app via install.sh (curl|bash) is the shipping path; notarized DMG + Homebrew cask (+ Sparkle) remain a future option
**Revised 2026-07-01** (in place; supersedes the original "notarized-DMG-for-MVP" framing below). Original decision was provisional and tagged "revisit after signing setup"; reality has settled, so this ADR now records what production actually ships.
**Decision:** Production ships a single **ad-hoc-signed `Houdini.app`** distributed via **`install.sh` (`curl | bash`)**, pinned to the current release tag. This is the **intended** distribution channel today, not a stopgap — it is the concrete expression of ADR-010's single-version rule (one advertised version, one install path, installer always re-fetched from the current tag). `install.sh` keeps its advertised guarantees: it **verifies SHA-256** against `SHASUMS256.txt` before install, installs **without `sudo`**, avoids a **Gatekeeper prompt** (ad-hoc-signed; quarantine handled so there is no multi-step System Settings ordeal), and **offers** a launch-at-login item rather than forcing it. A **signed + notarized DMG** ($99 Apple Developer Program), a **Homebrew cask** secondary channel, and **Sparkle** auto-update remain a documented **future** option, to be adopted if/when broader reach or one-click DMG install is wanted — not a blocker for the current release.
**Why:** The one-liner installer gives non-technical users a clean, one-command install today with integrity + least-privilege guarantees, and no paid Apple program is required to ship it. Keeping exactly one advertised version + one install path is the smallest correct distribution surface (ADR-010). (*Corrected 2026-07-03:* re-fetching `install.sh` from the current tag protects only copies fetched fresh from the site/README — a saved copy of an old one-liner *can* point at a dead artifact, and the v0.3.0 one now 404s. Under ADR-010's revised keep-superseded-releases rule this stops being possible for future versions.) The notarized-DMG path (and Homebrew, which also requires notarization and mainly reaches technical users) buys a nicer double-click install and auto-update, but at the cost of the $99 program and more signing machinery; it is worth revisiting later, but is not needed for the current single-version release.
**Consequence / trade-off:** `curl | bash` asks users to trust a piped install script; we counter that with the SHA-256 verification, no-`sudo` install, and an open, auditable `install.sh` (see `RELEASE.md`). This ADR does not add a Houdini server or move any credential off-device (ADR-005 / ADR-011 unchanged), and it does not add any site-side install UI beyond the single one-liner the site already advertises (consistent with ADR-010/011).
**Future decision (deferred, not blocking):** if we later want one-click DMG install and Sparkle auto-update, decide then whether to pay the $99 Apple Developer Program and stand up the notarize + staple + cask pipeline.

## ADR-007 — Pluggable provider adapters
**Decision:** Every provider implements one `UsageProvider` protocol with capability flags (`usagePct`, `resetTimer`, `dollarBalance`). The registry + UI adapt to whatever a provider can supply.
**Why:** Providers differ wildly (Claude has %, OpenAI Platform has $, ChatGPT Plus has almost nothing). A capability-driven model lets us add providers without touching the UI core.

## ADR-008 — Mobile is a native iOS app (cookie auth), not a PWA
**Decision:** The iPhone version is a **native SwiftUI app** (+ WidgetKit Home/Lock Screen widgets) that signs into claude.ai in an in-app `WKWebView`, captures the `sessionKey` cookie, stores it in the **iOS Keychain**, and calls the same `claude.ai` JSON endpoints via native `URLSession`. It reuses `FetcherCore`'s **cookie** path verbatim (`ClaudeCookieProvider` + `ClaudeUsageParser`); there is no Claude Code OAuth token on a phone, so the cookie path — the Mac app's *fallback* — becomes the iOS *primary*. FetcherCore was made iOS-compilable by guarding its only macOS-only dependency (`Foundation.Process`, in `CredentialStore.cliReadGenericPassword` and `ClaudeOAuthProvider.detectedClientVersion`) behind `#if os(macOS)`; the macOS build is unchanged (see `apps/ios/PLAN.md` §5).
**Why a native app, not a PWA:** A browser can't do this honestly. (1) **CORS** — a page on `houdini.salomao.org` calling `claude.ai/api/.../usage` is cross-origin and claude.ai doesn't allow it; native `URLSession` is not a browser and isn't subject to CORS. (2) **httpOnly** — `sessionKey` is an httpOnly cookie, unreadable from `document.cookie`; only a privileged native cookie store (`WKHTTPCookieStore`) can read it. The only way to make a PWA work is a **server proxy holding the user's cookie**, which would break the core privacy promise (ADR-005). So native is the *only* honest path.
**Trade-off / consequences:** (a) **Refresh** — iOS widgets inherit the same Apple budget as ADR-002 (~15–30 min, *not* 60s); the app refreshes on open/foreground; copy stays "updated X min ago". We promise 60s nowhere on iOS. (b) **Distribution** — unlike the Mac app there is **no free install-by-link**: shipping to others requires the **Apple Developer Program ($99/yr) + Xcode**, via TestFlight then the App Store (extends ADR-006; iOS removes macOS's un-paid escape hatches). (c) **Android** is a *future*, separate Kotlin app using the same cookie approach — not built now. None of the build/ship steps are possible on this CommandLineTools-only machine, so today's work is scaffold + an iOS-ready core only.

## ADR-009 — Rebrand "Tally" → "Houdini"
**Decision:** Rename the product, repo, app, CLI, and all user-facing surfaces from **Tally** to **Houdini** (`v0.2.0`). The menu-bar SPM target is `HoudiniApp` — case-distinct from the `houdini` CLI target, because SwiftPM keys each target's build tree off `<TargetName>.build/` and on case-insensitive APFS `Houdini.build/` and `houdini.build/` are the *same* folder, so equal-but-for-case names collide and the app's objects never get emitted. The shipped bundle binary is still `Houdini`. Bundle id → `org.salomao.houdini`; Keychain service → `Houdini-claude-session`. No credential migration — the user base is ~0.
**Why:** (1) **Collision + saturation** — "Tally" already names a shipping AI-usage tool (`ai-tally.app`) and is a heavily-used generic app word; it offered no defensible identity. (2) **Positioning** — the product is broadening from "Claude usage" to a **multi-provider AI usage + cost** platform; a distinctive, ownable name with a clear metaphor (the escapist who **reveals what's hidden** → "see your usage and spend, revealed") carries that story far better than a literal "tally". (3) **Identity** — "Houdini" unlocks a premium, characterful brand (top-hat mark, stage spotlight, gold "reveal" spark) that a utilitarian name did not.
**Trade-off / consequences (accepted):** "Houdini" is a crowded search term — **SideFX Houdini** (3D software) and **CSS Houdini** (web APIs) dominate organic results, so discovery leans on the `houdini.salomao.org` domain, the precise product descriptor in titles/OG, and direct/word-of-mouth rather than ranking for the bare word. Judged worth it for a memorable, on-metaphor brand over a generic, already-taken one. `tally.salomao.org` 301-redirects to the new domain so no links break.

## ADR-010 — Single-version production hygiene (no stale releases, no "coming soon")
**Revised 2026-07-03** (in place; changes the prune rule, keeps the single-advertised-version rule). Deleting old releases/tags proved harmful, not hygienic: the v0.3.0 one-liner now 404s, rollback to a known-good version is impossible, and a future `houdini update <version>` would target a null set (audit INS-03). The prune rule is therefore rescoped: **prune only the *pointers*** (site copy, `README`, the pinned one-liner, anything that advertises a version), **keep superseded releases and their tags** — each old release is retitled "**vX.Y.Z (superseded — do not install)**" and keeps its assets — and enable GitHub **Immutable Releases** on the repo so published assets can't be silently altered. Exactly **one** version is ever *advertised*; old versions remain *resolvable*, clearly marked, for rollback and update tooling. Also corrected: the bump+publish+prune steps were never "scripted to run as one unit" — publishing is CI's job (`release.yml`, the sole verified publisher — see RELEASE.md), and the pointer-prune is a checklist step there.
**Decision (original, 2026-06, prune rule superseded above):** Production carries exactly **one** advertised version at a time. Every production release: (1) **bumps** the version, (2) **publishes** the new release + verified installer, and (3) **removes** every obsolete GitHub release, git tag, and installer artifact so they can't be installed by mistake. The site, `README`, and the install one-liner reference **only the current version**. Production never ships a "coming soon" / "Soon" / "next milestone" placeholder; a surface is either real and shown, or absent. When a feature ships, the UI is **adapted** to absorb it (re-frame the relevant section) rather than having a new loose block stacked on. The procedure is the checklist in `RELEASE.md`. See ADR-009 for the rename that motivated the first cleanup (the obsolete `v0.1.0`/`v0.1.1` "Tally" releases carried broken one-liners and were deleted under this rule).
**Why:** Multiple *advertised* versions mean multiple install paths, and old pinned one-liners keep "working" while pointing at dead/renamed artifacts — every stale pointer is a support liability and a trust dent. "Coming soon" copy in production reads as vaporware and ages badly; honest products show what exists today. One advertised version + one install path is the smallest correct surface — but keeping superseded releases resolvable (clearly marked) is what makes rollback and self-update honest.
**Trade-off:** Superseded releases remain downloadable by someone who ignores the "do not install" retitle (accepted — the alternative, dead links and no rollback, is worse). Immutable Releases means a published asset can never be fixed in place — a bad release is superseded by a new version, never patched silently (that is the point).

## ADR-011 — Multi-provider direction; provider API keys never touch the frontend
**Decision:** Houdini is a **multi-provider** AI-usage + cost tool. The user-visible product is a single app with a **provider switcher in the app's own Settings** (not on the website). **Claude (Pro/Max)** is the primary, live provider (Keychain OAuth token or a one-time claude.ai session — see ADR-005 / `PROVIDERS.md`). **OpenAI Platform** is the planned **second** provider, connected with an **organization admin key**. That admin key — and any provider API/admin key, ever — is entered **only in the native app's Settings and stored only in the macOS Keychain**. It is **never** placed in the website, in any frontend/JS bundle, in environment variables shipped to the browser, in `config.ts`, or anywhere in the repo / version control. The website shows **no per-provider key UI and no visible OpenAI placeholder**; capability is expressed as one honest line ("Works with Claude today — built to track every AI you pay for").
**Why:** (1) **Security** — an API/admin key in frontend or repo code is a credential leak by construction; it would be world-readable in the bundle or git history. The only place a secret belongs is the OS Keychain on the user's own machine, read by native code (extends ADR-005: no Houdini server, no secret in transit to us). (2) **Honesty** — a dead provider grid with "Soon" badges advertises capability that isn't there (ADR-010); one honest capability line is truthful and ages well. (3) **Architecture** — the capability-driven adapter model (ADR-007) means a new provider is added in the core + Settings, never by reshaping the marketing site.
**Trade-off:** OpenAI's admin-API surfaces org-wide cost/usage, not a clean per-user gauge (ADR-004), so its UX is "$ this period + tokens", not a utilization %. The switcher and the OpenAI adapter are **not built in this round** — this ADR fixes the direction and the hard "keys never on the frontend/site/repo" rule so later implementation can't drift.

## ADR-012 — Claude subscription auth (OAuth token / claude.ai cookie): keep read-only, freeze expansion (decided)
**Status:** Decided 2026-07-01 (supersedes the initial "under review" logging). Revisit if Anthropic's terms/enforcement change or if the product pivots.
**Context:** Houdini's live Claude provider (v0.4.0) reads the user's Claude Code OAuth token (Keychain `"Claude Code-credentials"` / `~/.claude/.credentials.json`) or a claude.ai session cookie, then polls Anthropic's usage endpoints (`api.anthropic.com/api/oauth/usage` / `claude.ai/api/organizations/{org}/usage`) ~every 60s. In early 2026 Anthropic clarified and began enforcing that (1) Consumer Terms §3.7 forbid automated/script access to the Services except via an Anthropic API key or where explicitly permitted, and (2) OAuth tokens from Free/Pro/Max accounts may not be used "in any other product, tool, or service" — OAuth is intended only for Claude Code and claude.ai. Enforcement is active (account bans). Both of Houdini's Claude auth paths fall within the prohibited use. There is no ToS-sanctioned API for Pro/Max subscription limits; the only sanctioned usage API is the Admin Usage & Cost API (Admin key; API/Console consumption, not subscription limits).
**Decision:**
1. **Keep the Claude integration read-only**, using the user's existing on-device credential. Accept the residual ToS/account-ban risk, judged low for a local, read-only, non-commercial, open-source usage viewer that runs no inference.
2. **Do not seek Anthropic permission** (owner's call: small scale, non-commercial, open-source).
3. **Freeze expansion of the subscription-auth path:** no OAuth token refresh (the `refresher` stays `nil` — P1 slice (a)), no first-run PKCE "Connect" (candidate c), no cookie-flow hardening (candidate b) — these would escalate the signal that Houdini's traffic mimics the Claude Code client.
4. **Do not pivot** to API-key providers now; options (i)/(iv) (Anthropic Admin Usage & Cost API / lead with API-key providers) are retained as the future fallback if enforcement tightens.
5. **P1 consequence:** this caps P1 at slice (a) (broadened discovery of an existing credential). A true non-CLI user with **no** Claude Code credential anywhere cannot be served without escalating ToS risk, so that case is **out of scope** by decision.
6. **Mandatory for v1 (revised 2026-07-03; was "optional, deferred"):** a short user-facing transparency line — "Houdini reads your existing Claude credential; Anthropic's terms restrict third-party use of subscription OAuth; use at your discretion." — ships in **both** the app's Settings (next to the auth status) and the site's privacy page before v1.0.0 is tagged.
**Why:** The plain-text Consumer Terms + the Claude Code legal-and-compliance clause prohibit third-party use of subscription OAuth, and Anthropic bans accounts — but enforcement targets inference/token-arbitrage harnesses, whereas Houdini is a local, read-only usage viewer using the user's own credential, so the practical risk is low. Keeping it read-only and frozen preserves the product's core (Pro/Max limits at a glance) without escalating the signal; a full pivot would change what Houdini is and isn't warranted at current scale. The freeze on token refresh (decision 3) also has a decisive *technical* reason beyond ToS signal: OAuth refresh tokens may rotate on use, so if Houdini ever redeemed the user's refresh token it could invalidate the stored credential out from under the user's **own Claude Code CLI login**, stranding them — a read-only consumer must never mutate a credential it doesn't own. This is a risk/decision record, not legal advice.
**Consequence / trade-off:** The residual risk lands on each user's own Anthropic account, not on the project; the (now mandatory) transparency line above is the intended mitigation. If Anthropic tightens enforcement or the product grows, revisit — the fallback is (i)/(iv), which surface API usage/cost (not subscription limits) and would require revising `CONTEXT.md` / `README.md` / `PROVIDERS.md` / site copy. Related: ADR-005 (Keychain-only posture), ADR-010/011.

## ADR-013 — NSPanel is the desktop surface; WidgetKit is deferred (decided)
**Status:** Decided 2026-07-03 (the 2026-07 audit's "Option A hardened", ratified by the owner). Revisit only via the re-entry trigger below.
**Decision:**
1. The **NSPanel desktop widget is Houdini's desktop surface** — SwiftUI in a `.nonactivatingPanel` hosted *in the menu bar app's process*. This is a legitimate long-term architecture, not a stopgap: NSPanel is current, supported AppKit API, and it is the **only** surface that can deliver ~60s refresh (WidgetKit reload budgets — ADR-002), in-process sign-in, and free placement under today's distribution (ad-hoc-signed SPM executable via `install.sh` — ADR-006). No `.xcodeproj`, no extension target, no entitlement changes to the sacred install path.
2. A **WidgetKit widget (Notification Center or desktop) is deferred**, bundled with any future Apple **Developer Program decision** (the same bundle as iOS shipping / a notarized DMG — ADR-006's future option). It is not merely lower-priority; it is **triple hard-blocked** under the current distribution:
   - **App Groups require an Apple-issued Team ID on macOS 15+.** Apple DTS on ad-hoc signing + app-group containers: "no, this won't work. App group container protection, introduced in macOS 15, is based on your Team ID." (DevForums 776087; prompt-free access rules in 721701.)
   - **A Mac widget `.appex` must be sandboxed to appear in the widget gallery** (DevForums 685166, 718589) — and a sandboxed extension without an App Group cannot read the host app's snapshot, which the "app fetches, widget reads cache" model structurally requires.
   - **SwiftPM cannot produce a working `.appex`** — no extension target type exists, and a hand-wrapped SPM executable posing as an .appex exits before serving widget descriptors on macOS 26. A real Xcode app-extension target would be required, breaking the repo's no-`.xcodeproj`/`build.sh` convention.
   Public same-category precedent for all three gates: CodexBar issues #318/#533/#1095 (a menu-bar AI-usage app that hit these walls even with Developer-ID signing).
3. **`apps/widget/` is deleted** (ratified 2026-07-03; executed in the v1 audit's Phase D — it is a README-only placeholder with no buildable target; git history and this ADR preserve the intent). ADR-002 and ADR-003 are revised in place to match (Übersicht historical; NC widget planned-not-built; the menu bar app process is the sole 60s surface).
**Re-entry trigger:** adopting the Apple Developer Program (for iOS/TestFlight or a notarized DMG). If that bundle is ever taken: use an iOS-style `group.*` identifier authorized via a macOS provisioning profile (supported since Feb 2025), a real Xcode extension target, and study CodexBar #318/#533/#1095 first. Re-verify visuals against WWDC26 (macOS 27 "Golden Gate" WidgetKit changes) before implementing.
**Why:** The audit corrected the premise that had kept WidgetKit "pending": desktop WidgetKit placement is not new (it shipped with macOS 14 Sonoma, 2023), so there is no fresh capability to chase — while the three distribution gates above are confirmed hard blockers, not costs. Promoting the shipped NSPanel to *the* decided desktop surface ends the ambiguity: one desktop architecture, honest 60s freshness, zero signing/distribution risk.
**Trade-off:** No presence in Apple's widget gallery, and the desktop widget lives only while the menu bar app runs (accepted — the app is the product). Keeping severity legible without relying on hue (gauge arc + numeral) stays mandatory on all supported macOS versions, since the panel must match what a future monochrome-rendered WidgetKit surface would enforce anyway.
